# Exakte Versionen für die CI (Lint, mypy, pytest, Lizenz-Scan) UND für die
# Container-Images: core/Dockerfile und das Demo-Image installieren mit
# `pip install -c requirements-ci.txt` (seit 2026-11-27) -- `-c` legt nur
# Versionen fest, Test-Werkzeuge landen nicht im Image. Jede Änderung hier
# ändert damit das ausgelieferte Image: vor dem nächsten Release den
# Probelauf `gh workflow run release.yml` (Bau + Trivy-Scan). Fehlt hier ein
# Laufzeitpaket, bricht der Image-Bau mit dessen Namen ab.
#
# Warum: pyproject.toml nennt nur Untergrenzen (">="). Ohne diese Datei holte
# die CI bei jedem Lauf die neueste Version jeder Bibliothek; am 2026-09-24
# wurde main dadurch rot, ohne dass sich am Code etwas geändert hatte
# (SQLAlchemy 2.1.0 änderte die Typisierung von func.max). Jetzt ändern sich
# Versionen nur noch per Commit -- in der Regel über einen Dependabot-PR, dessen
# CI-Lauf das Update prüft, bevor es main erreicht.
#
# Die Datei enthält ALLE Pakete (auch transitive), samt PostgreSQL-Treiber
# (Extra `postgres`): Ohne ihn liefen Typprüfung und Tests des Treibercodes
# nicht mit. Die CI installiert sie mit `pip install -r` und procworks danach
# mit `--no-deps`; `pip check` schlägt fehl, wenn eine Abhängigkeit fehlt. Der
# Lizenz-Scan nimmt die Datei nur als Constraints für die Laufzeitpakete
# (ohne Extra) und sieht den Treiber (LGPL-3.0) deshalb nicht -- dessen
# Einordnung steht in THIRD-PARTY-NOTICES.md. Neu erzeugen, wenn sich die
# Abhängigkeiten in pyproject.toml ändern (Linux/CPython 3.12 ist maßgeblich;
# macOS löst derzeit dieselbe Menge auf):
#
#   python3.12 -m venv /tmp/lock && /tmp/lock/bin/pip install -U pip
#   /tmp/lock/bin/pip install -e ".[dev,postgres]" pip-licenses
#   /tmp/lock/bin/pip freeze --exclude-editable  # Ausgabe unter diesen Kopf
#
